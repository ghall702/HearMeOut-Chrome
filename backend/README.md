# Backend changes for the Chrome extension

The extension needs **one** thing the live app doesn't have yet: a way to sign in with Google and
get credentials for the existing `/api/public/v1` endpoints without pasting an API key. Everything
else (uploads, the media server, finalising, transcription, share/embed links, the Gmail card image)
uses the existing API unchanged.

`hearmeout-extension-auth.patch` applies to the Hear Me Out app source (`git apply` from the app's
root). It adds no tables, no migrations and no secrets, and doesn't change behaviour for the web app
or for `hmo_` API keys.

## What it adds

| File | Purpose |
|---|---|
| `src/routes/extension.connect.tsx` | Approval page at `/extension/connect`, opened by the extension through `chrome.identity.launchWebAuthFlow`. It uses the app's existing Google sign-in (Lovable Cloud Auth, `prompt=select_account`), shows which account is signed in, and has **Connect this Chrome profile**, **Use a different account** and **Cancel** buttons. |
| `src/lib/extension-auth.functions.ts` | `createExtensionGrant` server function. It needs the signed-in user's Supabase session (`requireSupabaseAuth`), and it only accepts redirect URIs of the form `https://<extension-id>.chromiumapp.org/`. |
| `src/lib/extension-auth.server.ts` | Creates a **single-use** Supabase magic-link token hash with `auth.admin.generateLink`. No email is sent. It also exchanges the hash for a new Supabase session, refreshes that session, revokes it, and checks the allow-list. |
| `src/routes/api/public/v1/extension.token.ts` | `POST {grant_type:"token_hash"\|"refresh_token"}` returns `{access_token, refresh_token, expires_at, user}`. A disallowed email gets 403 and a bad grant gets 401. |
| `src/routes/api/public/v1/extension.signout.ts` | Revokes only the extension's session (`admin.signOut(jwt, "local")`). The web app stays signed in. |
| `src/routes/api/public/v1/recordings.$id.upload-url.ts` | Issues a fresh upload token for a recording that's still `pending`, so the extension can retry an upload after the token expires without creating a duplicate recording. It returns 409 if the recording is already finalised. |
| `src/lib/apikeys.server.ts` | `authenticateApiKey` now accepts **either** `Bearer hmo_…` (unchanged) **or** `Bearer <Supabase access token>`. The token is verified with `auth.getUser`, so revoked sessions are rejected, and its email must be on `ALLOWED_EMAILS`. |
| `src/routes/index.tsx` | 4 lines. If Google sign-in was started from the connect page and the OAuth broker returns to `/`, the page sends you back to `/extension/connect`. |
| `src/test/extension-auth.test.ts` | Tests for redirect validation, the extension-ID allow-list, the email allow-list and the session payload. |
| `src/routeTree.gen.ts` | Regenerated by the TanStack router plugin. Lovable regenerates this file itself. |

## How the flow works

```
Extension (service worker)                 Hear Me Out web app                 Supabase Auth
──────────────────────────                 ───────────────────                 ─────────────
launchWebAuthFlow ───────────────────────▶ /extension/connect?redirect_uri=https://<id>.chromiumapp.org/&state=…
                                           Google sign-in (existing flow, allow-list enforced by DB trigger)
                                           user clicks "Connect this Chrome profile"
                                           createExtensionGrant ─────────────▶ admin.generateLink (no email)
◀── https://<id>.chromiumapp.org/#token_hash=…&state=…   (only this extension can receive this URL)
POST /api/public/v1/extension/token ─────▶ verifyOtp(token_hash) ────────────▶ new session for the extension
◀── { access_token (≈1 h), refresh_token, user }
Authorization: Bearer <access_token> on /api/public/v1/uploads, /finalize, /recordings …
```

Security properties:

* The grant is single-use and short-lived (Supabase's OTP expiry). It's delivered in a URL
  fragment to a `chromiumapp.org` address, which Chrome hands only to the extension with that
  ID. The extension also checks a random `state` value.
* The extension gets its **own** Supabase session, separate from the web app's. Sign-out in the
  extension revokes only that session, and refresh-token rotation in one doesn't affect the other.
* Access tokens are short-lived JWTs that the extension refreshes. The allow-list is checked when
  the grant is minted, when it's exchanged, on every refresh and on every API call.
* The media gateway secret stays on the server. The extension still receives only the per-file
  upload token that `/api/public/v1/uploads` already returns.

## Deploying

1. Apply the patch to the app repository and let Lovable rebuild:
   ```bash
   git apply /path/to/HearMeOut-Chrome/backend/hearmeout-extension-auth.patch
   ```
2. **Recommended:** add a non-secret environment variable that allow-lists the extension ID:
   ```
   HMO_EXTENSION_IDS=lphpbndpbbdgoglbgglgeckecbeilpjn
   ```
   This ID is fixed by the `key` in the extension's manifest, so it's the same in every Chrome
   profile and on every computer. If you publish to the Chrome Web Store, add the store-assigned ID
   too (comma-separated). If the variable isn't set, any extension can show your approval page, but
   only after you approve it yourself on that page.
3. Nothing else is needed: no database migration and no new secret. The endpoints use the existing
   `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SERVICE_ROLE_KEY`.

### Notes

* **Media server CORS.** The extension uploads from the `chrome-extension://` origin. The manifest
  lists `https://mediahub-lm-1.georgehalltuition.com/*` in `host_permissions`, so Chrome lets those
  requests through without the gateway's `HEARMEOUT_ALLOWED_ORIGINS` list. You don't need to change
  the gateway.
* **Transcription.** The extension calls `finalize` with `transcribe:false` first, so the share links
  appear straight away. It then calls `finalize` again with `transcribe:true` to start the app's
  existing transcription. That second call runs transcription synchronously, as it does today. If it
  is ever interrupted, the recording page's existing **retry** action in the web app still works.
